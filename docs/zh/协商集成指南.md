# A2A-T 协商集成指南

本指南说明如何将 A2A-T 的协商能力（**Negotiation-T**）集成到您自己的客户端与服务端 Agent 中：
SDK 提供什么、业务系统提供什么、七步集成路径，以及从 demo 走向生产时需要替换什么。以
[ran-energy-saving 样例](../../a2a-t-sample/ran-energy-saving/README-zh.md)作为贯穿示例——下文的
每处代码引用都指向仓库中当前可读的文件。

> 前置阅读：SDK 的集成基础（安装、LLM 配置、提示词生成与校验）见
> [开发指南.md](开发指南.md)，本指南默认您已掌握这些内容，聚焦协商层。自定义业务模板见该指南
> §1.5，在下文步骤 1 中引用。

## 1. 概述与架构

协商是一次两报文的往返交互：当 Task-T 校验以某条内容错误码失败、且服务端倾向于通过对话而非
直接拒绝来解决时，由服务端发起：

```text
客户端                                        服务端
  |  Task-T 任务请求（第 1 轮）                 |
  |------------------------------------------->|
  |           内容校验失败；错误码选择协商类型
  |  TASK_STATE_INPUT_REQUIRED                 |
  |  + Negotiation-T propose                   |
  |<-------------------------------------------|   第 1 轮：服务端发起 propose
  |  您的 NegotiationResponseProvider 决策（accept / reject / abort）
  |  Task-T 任务请求 + Negotiation-T accept（第 2 轮）
  |------------------------------------------->|
  |           提示词校验通过：执行协商后的任务
  |  TASK_STATE_WORKING ... / 报告 artifact    |
  |  TASK_STATE_COMPLETED                      |
  |<-------------------------------------------|
```

职责分界：

| 关注点 | SDK 提供 | 您提供 |
| --- | --- | --- |
| 门面（Facade） | `A2ATClient` / `A2ATServer`（[src/a2a_t/client/a2at_client.py](../../src/a2a_t/client/a2at_client.py)、[src/a2a_t/server/a2at_server.py](../../src/a2a_t/server/a2at_server.py)） | 携带您的 `.env`（`env_path`）构造 |
| Task-T 提示词生成 | `generate_task_prompt_from_text` / `generate_task_prompt_from_data_with_schema` | 自然语言输入与模板选择 |
| 模板与 schema | 模板管线：内置资源 + `local_file` 本地加载（开发指南 §1.5） | 您的业务模板、槽位定义与调用方参数 schema |
| 任务校验 | `validate_task_prompt_and_data_filling` 与结构化的按槽位错误模型（`ContentValidationError` 携带 `exc.errors`，含 `slot_name` / `code` / `message`） | 失败的错误码对您的业务意味着什么——协商还是拒绝（步骤 5） |
| 协商报文 | 每个门面 12 个方法——`generate_negotiation_{propose,accept,reject,abort}_prompt_from_data` / `_from_text` 加 `validate_{propose,accept,reject,abort}_prompt_and_data_filling`——基于类型化内容模型；42 个固定错误码；双语消息模板 | 何时开启协商、往协商里放什么内容 |
| 协商会话 | `negotiationContext` metadata 映射（`id` / `round` / `max_rounds` / `performative`）；SDK 本身无状态 | 无——会话状态随报文往返 |
| 任务执行 | 仅 A2A 发射语义（每条进度文本变为一次 `TASK_STATE_WORKING` 状态更新；结果变为报告 artifact；异常变为 `TASK_STATE_FAILED`） | 实际业务执行——`TaskExecutionService` 接缝（步骤 3） |
| 协商应答 | 第 2 轮的报文机制：重新生成 Task-T 提示词、构建类型化 accept、推进会话、经所选传输发送 | 如何应答的决策——`NegotiationResponseProvider` 接缝（步骤 4） |
| 传输 | 经官方 `a2a-sdk` 的 A2A 流式（SSE）与推送通知（webhook） | 所选传输的部署与安全 |
| LLM | OpenAI 兼容调用链（provider、model、重试、超时） | LLM 端点与 API key——离线运行可用样例的 mock |
| Agent 发现 | — | 注册中心（样例自带一个 mock） |

**一句话分界：** SDK 拥有报文——消息渲染、校验、协商会话映射与传输机制；您的系统拥有业务——
哪些模板与参数描述您的任务、校验失败何时转为协商、协商后的任务如何在您的 EMS/NMS 中执行、以及
您这一侧如何决定应答 propose。ran-energy-saving 样例用两个命名的集成接缝把这个分界钉在代码里
——服务端 `TaskExecutionService` 与客户端 `NegotiationResponseProvider`，各自在装配处带有
`INTEGRATION POINT` 标注——分界在 IDE 里可发现，而不只是写在文档里。

## 2. 七步集成路径

### 步骤 1 — 定义 Task-T 模板与调用方参数 schema

协商谈的是*您的*任务，因此 Task-T 模板（渲染出的提示词）、槽位定义与调用方参数 schema 是其余
一切的地基。编写步骤、`local_file` 资源目录结构与 `templateUri` 映射规则见
[开发指南.md §1.5 加载自定义模板](开发指南.md#15-加载自定义模板)——直接遵循该节，不必另创目录
结构。

贯穿示例：样例的模板为 `Task-T/network-layer/ran-energy-saving/v1`
（`ENERGY_SAVING_TEMPLATE_URI`，见
[src/client/scenario_data.py](../../a2a-t-sample/ran-energy-saving/src/client/scenario_data.py)），
双端共享的调用方参数 schema 为
[src/common/task_schema.py](../../a2a-t-sample/ran-energy-saving/src/common/task_schema.py) 中的
`TASK_PARAM_SCHEMA`（`operationType`、`region`、`energySavingGoal`、`guaranteedThroughputTarget`）。
协商第 2 轮补全的正是这份 schema：客户端用 `generate_task_prompt_from_data_with_schema` 从补全后
的参数重新生成 Task-T 提示词。

### 步骤 2 — 配置 LLM

SDK 经 OpenAI 兼容调用链访问外部 LLM；配置项（`A2AT_LLM_API_KEY`、`A2AT_LLM_PROVIDER`、
`A2AT_LLM_MODEL`、`A2AT_LLM_BASE_URL`、`A2AT_LLM_TIMEOUT_SECONDS`、`A2AT_LLM_MAX_ATTEMPTS` 等）
见开发指南 §1.7。

协商路径上 LLM 的实际使用方式：

- 槽位抽取（`generate_task_prompt_from_text`）始终运行一次 LLM 调用。
- 协商的 **fromData** 通道（`generate_negotiation_*_prompt_from_data`）是确定性的——将类型化内容
  渲染到模板上，不调用 LLM。
- **fromText** 通道（`generate_negotiation_*_prompt_from_text`）每生成一条消息多一次抽取 LLM
  调用。

因此仅用 fromData 的集成主要在最初的提示词生成时需要 LLM。离线/CI 运行可以完全跳过 LLM：样例
中 `A2AT_LLM_API_KEY` 为空时启用随包的按 schema 路由的 mock LLM
（[resources/mock_llm/{zh-CN,en-US}/](../../a2a-t-sample/ran-energy-saving/resources/mock_llm)，由
`src/common/` 提供），回放脚本化的槽位抽取与内容校验应答。

### 步骤 3 — 实现服务端 `TaskExecutionService`

服务端接缝是样例
[src/server/task_execution.py](../../a2a-t-sample/ran-energy-saving/src/server/task_execution.py)
中的 `TaskExecutionService` Protocol：

```python
@runtime_checkable
class TaskExecutionService(Protocol):
    def execute(
        self, params: dict[str, object], emit_progress: Callable[[str], Awaitable[None]]
    ) -> Awaitable[TaskExecutionResult]: ...

@dataclass(slots=True, frozen=True)
class TaskExecutionResult:
    report_name: str       # 成为 artifact 名称
    report_text: str       # 成为 artifact 的标签 text part
    report_metadata: str   # 报告正文，携带在 artifact.metadata[Task-T/v1] 中
```

分工由 flow 固定
（[server_flow.py](../../a2a-t-sample/ran-energy-saving/src/server/server_flow.py)）：

- `params` 携带 `validate_task_prompt_and_data_filling` 抽取出的 Task-T 已填参数（样例 schema 为
  object 形状，因此是 `dict[str, object]`）。
- 每次调用 `emit_progress(text)` 在报文上成为一次 `TASK_STATE_WORKING` 状态更新。
- 返回的 `TaskExecutionResult` 成为报告 artifact（一次 `TaskArtifactUpdateEvent`）。
- 实现抛出的异常被 flow 捕获，发出带通用文案 `Task execution failed: {exc}` 的
  `TASK_STATE_FAILED` 并重新抛出——流式与终态语义免费获得，您只需产出进度文本与结果。
- `execute` 是同步方法、返回 awaitable；`async def` 实现即满足（`Coroutine` 是 `Awaitable`）。若
  决策内部需要异步（等待远端系统），请在实现内部自行处理。

一个贴近真实的最小骨架——带进度映射的 EMS/NMS 北向调用：

```python
from collections.abc import Awaitable, Callable

from server.task_execution import TaskExecutionResult, TaskExecutionService


class EmsEnergySavingExecutionService:
    """经 EMS 北向接口执行协商后的节能任务。"""

    async def execute(
        self, params: dict[str, object], emit_progress: Callable[[str], Awaitable[None]]
    ) -> TaskExecutionResult:
        region = str(params["region"])
        await emit_progress(f"Connecting to the EMS for region {region}")
        plan = await self._ems.create_energy_saving_plan(**params)  # 您的 EMS/NMS 调用
        await emit_progress(f"Energy-saving plan {plan.id} activated")
        return TaskExecutionResult(
            report_name="energy saving intent report",
            report_text=plan.summary_text,     # artifact 标签 text part
            report_metadata=plan.report_json,  # 报告正文在 artifact.metadata[Task-T/v1]
        )
```

装配处——
[src/server/server_main.py](../../a2a-t-sample/ran-energy-saving/src/server/server_main.py) 的
`build_server_runtime`：

```python
# INTEGRATION POINT: replace Uc1DemoExecutionService with your business execution service
# (the server flow depends only on the TaskExecutionService Protocol it implements).
execution_service: TaskExecutionService = EmsEnergySavingExecutionService()
```

同文件中的 demo 实现 `Uc1DemoExecutionService` 委托
[src/server/constants_data.py](../../a2a-t-sample/ran-energy-saving/src/server/constants_data.py)
中的静态 UC1 数据（脚本化进度步骤 + 意图报告）——这正是您的实现要替换的部分。

### 步骤 4 — 实现客户端 `NegotiationResponseProvider`

客户端接缝是
[src/client/negotiation_response.py](../../a2a-t-sample/ran-energy-saving/src/client/negotiation_response.py)
中的 `NegotiationResponseProvider` Protocol：

```python
@runtime_checkable
class NegotiationResponseProvider(Protocol):
    def respond(
        self, propose: NegotiationProposeView, session: NegotiationContext
    ) -> NegotiationDecision: ...

@dataclass(frozen=True, slots=True)
class NegotiationProposeView:
    kind: str           # flow 解析出的协商类型（配置的 flag，否则按 propose 的 templateUri 分派）
    template_uri: str   # propose 的 templateUri
    prompt_text: str    # propose 的渲染文本，逐字透传（flow 从不解析）

@dataclass(frozen=True, slots=True)
class NegotiationDecision:
    conclusion: Literal["accept", "reject", "abort"] # accept / reject / abort
    filled_params: dict[str, object] | None = None   # information accept：name->value 条目
    confirmed_intent: str | None = None              # target accept
    feasibility_summary: str | None = None           # feasibility accept
    reason: str | None = None                        # reject / abort
```

服务端以 `INPUT_REQUIRED` 的 Negotiation-T propose 应答第 1 轮时，客户端 flow 从报文 metadata
构建视图、调用 `respond`、并按决策行动
（[client_flow.py](../../a2a-t-sample/ran-energy-saving/src/client/client_flow.py)）：

- `accept` → 报文机制仍归 flow：它用调用方提供的补全参数重新生成 Task-T 提示词、按 propose 类型的
  决策字段（`filled_params` / `confirmed_intent` / `feasibility_summary`）构建类型化 accept、推进
  会话、并经所选传输发送第 2 轮。
- `reject` / `abort` → **本 demo 未接线**：flow 打日志
  `negotiation-decision: {conclusion} (not wired in this demo; see the integration guide)` 后结束
  流程、不发送任何报文。真正的扩展点是
  [client_flow.py](../../a2a-t-sample/ran-energy-saving/src/client/client_flow.py) 中
  `_plan_negotiation_accept` 的 reject/abort 分支——决策点（`respond`）只返回
  `NegotiationDecision`，无法发送报文。要真正发出去，请扩展该分支、仿照
  `_run_negotiation_accept_round`：以
  `session.next_round().with_performative(NegotiationPerformative.REJECT)` 推进会话，构建该类型的
  结束内容、conclusion 置为 `Reject`（决策的 `reason` 写入结束内容的 `failure_reason`），再用 SDK
  的 `generate_negotiation_reject_prompt_from_data` / `..._from_text`（按 channel 选）生成第 2 轮
  reject——见 §5.2。
- `respond` 是同步的——flow 在决策点阻塞。需要异步的客户实现（人工确认 UI、上游系统调用）在
  实现内部自行处理。

一个策略引擎风格的骨架，含一次 reject 决策：

```python
from a2a_t.core.metadata import NegotiationContext

from client.negotiation_response import NegotiationDecision, NegotiationProposeView


class PolicyNegotiationResponseProvider:
    """基于运营方策略引擎应答协商 propose。"""

    def respond(
        self, propose: NegotiationProposeView, session: NegotiationContext
    ) -> NegotiationDecision:
        if propose.kind == "target":
            intent = self._policy.align_target(propose.prompt_text)
            if intent is None:
                return NegotiationDecision(conclusion="reject", reason="target outside the operator policy")
            return NegotiationDecision(conclusion="accept", confirmed_intent=intent)
        if propose.kind == "feasibility":
            return NegotiationDecision(
                conclusion="accept", feasibility_summary=self._assess_feasibility(propose)
            )
        return NegotiationDecision(
            conclusion="accept", filled_params=self._cmdb.lookup_missing_items(propose.kind)
        )
```

装配处——
[src/client/client_main.py](../../a2a-t-sample/ran-energy-saving/src/client/client_main.py) 的
`main()`：

```python
# INTEGRATION POINT: replace ScriptedNegotiationResponseProvider with your negotiation
# response provider (human confirmation, policy engine, upstream system...)
negotiation_response_provider = PolicyNegotiationResponseProvider(...)
```

同文件中的 demo 实现 `ScriptedNegotiationResponseProvider` 封装
[src/client/scenario_data.py](../../a2a-t-sample/ran-energy-saving/src/client/scenario_data.py)
的脚本化应答——这正是您的实现要替换的部分。

> **Provider 替换什么——不替换什么。** Provider 只替换对 propose 的脚本化*应答*。Task-T 提示词
> 补全参数（样例中的 `negotiation_params`）在任何情况下都是 flow 的调用方输入：flow 需要它们来
> 重新生成第 2 轮的 Task-T 提示词，缺了它们协商不会开启。它们是 flow 拥有的报文机制，既不是
> provider 的输入，也不是脚本化应答数据。

### 步骤 5 — 错误码到协商类型的映射

样例用 [server_flow.py](../../a2a-t-sample/ran-energy-saving/src/server/server_flow.py) 中的模块级
常量决定*何时协商*：

```python
_NEGOTIATION_TYPE_BY_ERROR_CODE: dict[str, str] = {
    CONTENT_ERROR_CODE_INFORMATION: NEGOTIATION_TYPE_INFORMATION,   # content.param_missing    -> information
    CONTENT_ERROR_CODE_TARGET: NEGOTIATION_TYPE_TARGET,             # content.value_not_allowed -> target
    CONTENT_ERROR_CODE_FEASIBILITY: NEGOTIATION_TYPE_FEASIBILITY,   # content.semantic_conflict -> feasibility
}
```

`_resolve_negotiation_type` 用首条校验错误的码在该表中查出 propose 类型；其他码——或无码错误——
不选协商类型，任务照常被拒绝（`TASK_STATE_REJECTED`）。一条内置规则保留：只有当错误确实点名了
缺失槽位时才开启 information propose。

该映射是**样例层的约定，不是 SDK 契约**。报文是自描述的——每个 propose 携带各自的
`templateUri`（`Negotiation-T/{information,target,feasibility}-negotiation/propose/v1`），客户端
基于该 URI 分派 accept——因此您复制样例后可以随意编辑该常量：重映射错误码、为自有错误码增加
条目、或让某些码保持不映射而继续拒绝。

### 步骤 6 — 选择传输（SSE 或 webhook）

两种传输投递相同的任务事件；区别在客户端如何接收：

- **SSE 流式**（默认）：客户端保持流式 `message:send` 连接并即时消费事件——样例所有流程的默认
  路径。
- **Webhook 推送通知**：客户端非阻塞发送（`return_immediately`），在客户端进程内嵌的接收器上以
  webhook POST 接收每个事件。第 1 轮在请求上内联注册推送配置；第 2 轮在发送 accept 前经
  `POST /tasks/{id}/pushNotificationConfigs` REST 端点重新注册。服务端无条件装配推送机制，因此
  服务端没有模式开关。

选择方式与细节——参数、配置键、注册流程、token 鉴权、结束信号、空闲兜底——见样例 README：
[如何运行](../../a2a-t-sample/ran-energy-saving/README-zh.md#如何运行)（`--transport`、
`--webhook-port`）与
[Webhook 传输（A2A 推送通知）](../../a2a-t-sample/ran-energy-saving/README-zh.md#webhook-传输a2a-推送通知)。
协商往返在两种传输上逐语句一致。

### 步骤 7 — 先用 mock 验证，再上线

样例可完全离线运行：mock LLM（`A2AT_LLM_API_KEY` 为空）、mock 注册中心
（[src/registry/](../../a2a-t-sample/ran-energy-saving/src/registry)，端口 5001）与两个脚本化接缝。
先用它端到端验证模板、schema、错误码映射与传输选择，再按
[demo 到生产的替换清单](#4-demo-到生产的替换清单)逐项替换，每替换一项后重跑样例命令。

## 3. 三类协商的业务语义

Negotiation-T 固定三类 propose 外加类型无关的 abort；SDK 在
[src/a2a_t/negotiation/content/models.py](../../src/a2a_t/negotiation/content/models.py) 的类型化
模型中承载它们的内容。每类的 propose 由服务端渲染，对应的 accept 由客户端基于下述模型应答。

### information（信息协商）——服务端缺数据

**业务模式：** 任务请求缺少服务端执行所必需的参数。服务端点名缺失条目；客户端补全取值后任务
照常执行。

| | |
| --- | --- |
| Propose 内容 | `InformationProposeContent(items, relationship)`——`items` 为缺失条目，`NegotiationItem(name, value)` |
| 结束内容 | `InformationEndingContent(items)`——补全的条目 |
| 客户端决策字段 | `NegotiationDecision.filled_params`（name → value） |
| 模板 URI | `Negotiation-T/information-negotiation/propose/v1`、`.../accept-reject/v1` |

**业务示例：** 节能任务请求没有携带目标区域——服务端发起信息协商，点名缺失的 `region`；客户端
以 `{"region": "Songshanhu Administration Committee"}` 接受，任务随即执行。
样例输入：`run_demo.py --scenario negotiation`。

### target（目标协商）——双方对齐目标口径

**业务模式：** 请求的目标本身合法，但超出或偏离服务端能力的口径。服务端复述其对对方意图的
理解，并请求确认澄清后的目标——即一个只携带摘要与确认请求的确认请求轮。

| | |
| --- | --- |
| Propose 内容 | `TargetProposeContent(target_negotiation_description, intent_understanding, alignment_and_clarification, request_for_clarification, target_confirm_request)` |
| 结束内容 | `TargetEndingContent(confirmed_intent, failure_reason)`——恰有一个有意义，由 conclusion 决定（accept → 确认后的意图，reject → 失败原因） |
| 客户端决策字段 | `NegotiationDecision.confirmed_intent` |
| 模板 URI | `Negotiation-T/target-negotiation/propose/v1`、`.../accept-reject/v1` |

**业务示例：** 客户端为某小区请求 100Mbps 保障速率，而该小区能力上限更低——服务端复述意图并
请求客户端确认一个符合能力口径的目标；客户端确认其意图。
样例输入：`run_demo.py --negotiation target`。

### feasibility（可行性协商）——评估目标是否可达

**业务模式：** 所请求的目标在当前网络状态下可能不可达。服务端请求对冲突内容做可行性评估
（`action=REQUEST_FEASIBILITY_EVALUATION`）；当其评估为不可行时，可以改为提出替代方案
（`action=PROPOSE_ALTERNATIVE_ON_FAILURE`，携带 `infeasibility_details_and_proposal`）；确认请求
轮则请求对方确认一个评估为可行的结果。

| | |
| --- | --- |
| Propose 内容 | `FeasibilityProposeContent(feasibility_negotiation_description, action, contents_to_evaluate, infeasibility_details_and_proposal, feasibility_confirm_request)`——`action` 为 `NegotiationAction` 取值（[src/a2a_t/negotiation/content/enums.py](../../src/a2a_t/negotiation/content/enums.py)） |
| 结束内容 | `FeasibilityEndingContent(feasibility_summary)`——评估结果摘要 |
| 客户端决策字段 | `NegotiationDecision.feasibility_summary` |
| 模板 URI | `Negotiation-T/feasibility-negotiation/propose/v1`、`.../accept-reject/v1` |

**业务示例：** 30% 节能目标与 50Mbps 保障速率目标冲突——服务端请求对这两条冲突内容做可行性
评估；客户端以可行性摘要应答。
样例输入：`run_demo.py --negotiation feasibility --channel fromText`。

每类都有 reject 与 abort 结束（reject 复用该类的 `accept-reject` 模板；abort 使用公共的
`Negotiation-T/common/abort/v1` 模板，内容为 `NegotiationAbortContent(termination_reason)`）——
demo 现状见 §5.2。

## 5. 生产注意事项

### 5.1 终态与错误路径

- **校验失败** → 服务端发出 `TASK_STATE_REJECTED`（文案
  `Prompt validation failed: {validation_failure}`）而不是崩溃——这是映射表（步骤 5）未转为协商的
  错误码的归宿。
- **执行失败** → `TaskExecutionService` 抛出的异常变为 `TASK_STATE_FAILED`（通用文案
  `Task execution failed: {exc}`），flow 随后重新抛出。
- **正常结束** → 协商运行在第 2 轮 accept 校验通过、任务执行后以 `TASK_STATE_COMPLETED` 收尾；
  样例的默认（非协商）流程保持长时运行、不发终态。Webhook 客户端在任一 SDK 终态
  （`COMPLETED` / `FAILED` / `CANCELED` / `REJECTED`）结束流程——无事件到达时由空闲兜底结束
  （`A2AT_SAMPLE_WEBHOOK_IDLE_TIMEOUT`，默认 30 秒）。

### 5.2 协商轮次预算与 abort

- 会话上下文 `NegotiationContext(id, round, max_rounds, performative)`
  （[src/a2a_t/core/metadata.py](../../src/a2a_t/core/metadata.py)）约束一次协商最多进行多少轮
  （`DEFAULT_MAX_ROUNDS = 5`）。它不可变——推进到下一轮会产生新实例——并随每条消息的
  `negotiationContext` metadata 映射往返。
- **abort 与类型无关**：`NegotiationAbortContent(termination_reason)` 渲染到公共的
  `Negotiation-T/common/abort/v1` 模板（典型原因：达到轮次上限、超时、预算耗尽）。
- **demo 中的 reject/abort：** provider 给出的 `reject`/`abort` 决策*未接线到报文*——flow 打日志
  `negotiation-decision: {conclusion} (not wired in this demo; see the integration guide)` 后结束
  流程、不发送（与未处理 propose 相同的结束语义）。没有其他接缝：决策点（`respond`）只返回
  `NegotiationDecision`，无法发送报文。要真正发出去，请扩展 client_flow.py 中
  `_plan_negotiation_accept` 的 reject/abort 分支、仿照 `_run_negotiation_accept_round`：以
  `session.next_round().with_performative(NegotiationPerformative.REJECT)` 推进会话，构建该类型的
  结束内容、conclusion 置为 `Reject`（`TargetEndingContent.failure_reason` 携带决策的 `reason`；
  abort 则改用 `NegotiationAbortContent(termination_reason)`），再调用 SDK 的
  `generate_negotiation_reject_prompt_from_data`（reject 复用该类的 `accept-reject` 模板，如
  `Negotiation-T/feasibility-negotiation/accept-reject/v1`）或
  `generate_negotiation_abort_prompt_from_data`（公共的 `Negotiation-T/common/abort/v1` 模板）；
  两者在 `A2ATClient` 与 `A2ATServer` 上都有，`_from_text` 变体各多一次抽取 LLM 调用。
- **诊断您自己的 provider：** 另有两种 `negotiation-decision` 问题日志提示 flow 无法使用某个
  决策——未知 conclusion 时为 `unsupported conclusion {c!r}; staying on round 1`；propose 类型的
  accept 字段为 `None` 时为
  `the accept decision is missing <field> for the <kind> negotiation; staying on round 1`。两者
  都按未处理 propose 的方式结束流程。

### 5.3 Webhook 安全

推送接收器对每个 POST 校验 `X-A2A-Notification-Token` 头：不匹配应答 `401`（事件被丢弃），畸形
或无法识别的报文应答 `400`。demo 的静态共享 token（`A2AT_SAMPLE_WEBHOOK_TOKEN`，默认
`demo-webhook-token`）是 **demo 级**的——生产请使用 TLS 之上可轮换的逐客户端密钥，并把接收器
当作暴露在外的 HTTP 端点对待。空闲兜底（`A2AT_SAMPLE_WEBHOOK_IDLE_TIMEOUT`，默认 30 秒，每收到
一个事件即重置）防止停滞的流程永久挂起。

### 5.4 跨轮次的无状态 negotiationContext

SDK 不保存任何协商状态（开发指南 §1.2）：会话随每条消息的 `negotiationContext` metadata 映射
（`id` / `round` / `max_rounds` / `performative`）往返，第 2 轮重复第 1 轮的 `task_id` /
`context_id`。您的 provider 每轮收到解析后的 `NegotiationContext`；任何您想要的跨轮记忆——自动
拒绝前累计 propose 次数、关联上游工单、记住已给出过的方案——都是您的实现之事，以会话 `id` 为键。

## 6. 运行示例

[ran-energy-saving 样例](../../a2a-t-sample/ran-energy-saving/README-zh.md)是上文一切的贯穿示例。
其 README 记录了传输 / 协商类型 / 生成通道矩阵与全部运行参数
（[如何运行](../../a2a-t-sample/ran-energy-saving/README-zh.md#如何运行)）、报文上的协商往返
（[协商场景](../../a2a-t-sample/ran-energy-saving/README-zh.md#协商场景negotiation-t)）与 webhook
变体（[Webhook 传输](../../a2a-t-sample/ran-energy-saving/README-zh.md#webhook-传输a2a-推送通知)）。
快速开始：

```bash
cd a2a-t-sample/ran-energy-saving

python run_demo.py --transport webhook                            # webhook 传输，default 场景
```
